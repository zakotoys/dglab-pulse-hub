| 项目     | 内容                                                                                                                 |
| -------- | -------------------------------------------------------------------------------------------------------------------- |
| 状态     | Active / 实施基线                                                                                                    |
| 规划单位 | 可工作的端到端增量，而不是组件完成度                                                                                 |

本计划把现有 PRD/TRD 转换为可执行顺序。每个里程碑都必须留下一个可以运行、可以测试、可以继续扩展的产品；不得以“底层基本完成”代替端到端验收。

## 1. 规划原则

1. **先建立格式证据，再固化领域规则**：`.pulse`
   没有公开的完整官方文件规范，也没有内嵌版本号。样例事实、官方产品语义和社区推断必须分别标注。
2. **先做单文件闭环，再扩展批量与跨端**：首个闭环是“读取 -> 识别 -> 解析 -> 校验 -> 展开 -> 报告 -> 导出 -> 再导入”。
3. **核心先于外壳，但每层都可运行**：核心通过 Node 命令入口证明可用，Web 和 Electron 只编排同一用例，不复制规则。
4. **测试先于行为实现**：每个工作项先补失败测试或可复现夹具，再实现最小代码，最后重构。
5. **不实现猜测出来的兼容性**：没有可识别输入、目标输出和期望变更的升级规则，不进入实现。
6. **不保留废弃路径**：规则或接口尚未发布时直接修正；发布后通过明确的 schema/rule
   version 演进，不维护未采用的试验 API。

## 2. 当前事实与约束

| 事实                                                                             | 规划影响                                                                                                                                                                |
| -------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 工作区已有 core/application/contracts、CLI、HTTP API、Web 和 Electron 运行时代码 | M1-M4 的单文件、批量、编辑、预览和跨端契约可以独立运行；发布打包与生产门禁仍需单独验收                                                                                  |
| `.example` 有 16 个文件、69 个 section、1,686 个曲线点，且当前被 git 忽略        | 这些数字是当前工作区证据，不是假定干净 clone 也能得到的 fixture；M0 必须记录来源/再分发权，并决定是否提交只含统计和校验信息的 metadata manifest。CI 使用最小合成夹具    |
| 样例包含 1 至 10 个 section，启用 section 也可超过 3 个                          | 明确区分 `parse-supported`（解析器可接受 1..10）和 `app-verified`（目标 App 已验证）；官方 UI 的“三小节”描述不自动成为文件拒绝条件，4..10 不得未经验证就承诺 App 互操作 |
| 强度包含两位小数，自动点和锚点并存                                               | 解析阶段不得先取整；未编辑内容必须保留原始数值表达能力                                                                                                                  |
| 文件本身没有显式版本字段                                                         | `version` 不能伪造；识别结果使用 `formatProfile`、`ruleVersion` 和证据等级                                                                                              |
| 官方确认每个曲线竖条为 100 ms，脉冲元完整重复并向上取整                          | WaveformStream 的逻辑时间轴可以据此建立；物理频率映射仍需互操作夹具验证                                                                                                 |
| 设备传输不属于当前核心范围                                                       | M0-M4 不生成或发送 BLE/V3/V4 帧，不让设备能力阻塞文件工作台                                                                                                             |

当前 Electron 发布入口使用 Electron Forge；主进程和 sandbox
preload 在构建时分别 bundle，已在本机 macOS arm64 完成 package/make/启动检查。Release
workflow 已配置 Windows x64/ARM64 和 macOS Intel（Electron
x64）/ARM64 的独立安装包与便携 ZIP 任务；Windows/macOS hosted
runner 的实际安装、启动、签名和升级验证仍属于 M5 发布门禁，不能由本机结果代替。

样例统计和证据边界见 [本地语料分析](../research/pulse-corpus.md)。

### 规划中的词汇边界

- `parse-supported` 只表示本项目能按已冻结 grammar 消费输入；`app-verified`
  还必须有 App、平台、输入哈希、步骤和结果记录。`Not verified` 是证据状态，不是通过状态。
- 公共结果只暴露逻辑 metadata、`formatProfile`、`ruleVersion`、证据等级、状态、结果和诊断。绝对路径、临时路径和本地文件名只属于文件 adapter；没有外部证据时不得生成通用
  `version` 字段。
- 非阻断诊断可以与成功结果并存；取消是终态
  `cancelled`，不映射成失败或成功。每个异步任务还必须有明确的输出存活期、下载/关闭触发器、过期清理和停止清理行为。

## 4. 关键路径

```text
样例清单与语法画像
  -> 解析/诊断契约
  -> Pulse 语义校验
  -> WaveformStream 展开规则与资源预算
  -> result envelope / schema 契约
  -> 单文件应用用例
  -> HTTP 与 IPC adapter
  -> Web / Electron 工作区
  -> 编辑、批量与导出增强
  -> 生产部署门禁
```

任何阶段发现格式证据与当前规则冲突时，先更新研究记录和契约测试，再修改实现；不得在 UI 或 adapter 中添加局部例外。

## 5. 依赖与决策门槛

| 决策点                 | 最迟时间                   | 必须具备的证据                                                                                         | 未满足时的处理                                                        |
| ---------------------- | -------------------------- | ------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------- |
| 支持边界与互操作等级   | M0 退出前                  | `parse-supported`/`app-verified` 矩阵、1..10 section 结论、每项证据状态                                | 未验证项只可作为解析能力；不得进入 App 等价播放或发布承诺             |
| 频率/时长索引映射      | M1 stream 实现前           | 映射表来源、边界测试、四种模式 golden vectors、至少一份可复核互操作结果                                | 只展示索引和逻辑时间，不标成 Hz 或承诺 App 等价播放                   |
| 跨端结果契约           | M2 API 前                  | schema library 决策、status/result/diagnostics 字段、未知版本拒绝、direct/CLI/HTTP/IPC golden          | 禁止暴露 API；先完成契约和应用投影                                    |
| FileMetadata 公共边界  | M0 schema 草案前           | ADR-0003 与 TRD 字段定义完成对齐；`displayName`、format profile、ruleVersion、证据和状态的公开边界明确 | 不把路径、临时路径或未经证实的通用 `version` 放入公共 DTO             |
| 规范化小数格式         | M1 serializer 前           | 16 个样例往返、编辑后 App 导入测试                                                                     | 未编辑导出使用源快照；不开放会触发重写的编辑                          |
| VAL-006 作用域         | M4.5 编辑前                | PDR-0002 明确区分编辑插值与升级复用；各自的验收和证据范围进入追踪矩阵                                  | 在决策更新前保留原有 `Conditional` 门槛，不实现或宣称已验证的拆分路径 |
| Web 文件与任务生命周期 | M2 API 前；批量在 M4.2 前  | 同步/异步边界、成功/失败/取消/断开/停止/过期清理、下载描述、任务隔离；与 PDR-0003 一致                 | 未解决时只允许已验证的同步内存流程；不实现异步任务下载或持久化        |

| 账户/持久化/公开分享   | M5 以后单独立项            | 独立 PDR、威胁模型和删除策略                                                                           | M2-M5 保持无账户、临时处理                                            |

## 6. 工作项模板

每个实现工作项至少写明：

- 对应 PRD ID 和当前里程碑。
- 用户可观察的输入、成功结果和失败结果。
- 首个失败测试及所需夹具。
- 涉及的领域、应用、adapter 或展示边界。
- 新增/变更的 schema、diagnostic code 或 rule version。
- 资源上限、隐私和日志影响。
- 进入条件、阻塞条件、退出证据，以及该项是 `parse-supported`、`app-verified` 还是 `Not verified`。
- 完成证据：测试命令、样例输出或跨端契约结果。

不接受只以“创建模块”“搭好页面”“接入库”为完成条件的工作项。

## 7. 进度规则

- `Planned`：范围和验收已明确，但尚无失败测试。
- `In progress`：失败测试已提交，正在实现最小行为。
- `Verified`：自动化测试、人工验收和文档同步完成。
- `Conditional`：范围已列出，但必须先满足单独的证据门槛；不能以代码存在代替门槛。
- `Blocked`：存在明确外部证据或决策缺口，并记录解除条件。
- `Deferred`：经 PDR/ADR 明确移出当前发布，不以空实现占位。
- `Not verified`：互操作或人工证据尚未执行；不计入任何里程碑通过条件。

里程碑只有在 [质量门禁](quality-gates.md) 全部通过后才能标记完成。
