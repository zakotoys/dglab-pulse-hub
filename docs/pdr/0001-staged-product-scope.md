# PDR-0001：分层交付与首发范围

## 状态

Accepted — 2026-08-30

## 背景

PRD 同时描述核心库、CLI、Electron、Web API、批处理、QR、图片和编辑器。仓库当前没有实现或工程骨架。如果同时铺开全部交付形态，格式错误会被复制到多个客户端，且任何一端都不能形成稳定闭环。

项目原则要求从最小可运行产品逐层增长，并且不为尚未发布的路径保留兼容层。

## 决策

产品按以下顺序交付：

1. **内部可用 M1**：核心库 + CLI，完成 `.pulse` 单文件导入、校验、index-based stream、metadata、规范导出和再导入等价。
2. **首个用户可用版本 M2**：在 M1 契约上交付 Web 与 Electron 单文件工作台。两端共享领域结果，Electron 离线运行。
3. **首个完整版本的条件能力 M3/M4**：批处理、图像、QR、编辑与规则变换逐个加入；QR 和规则变换只有证据门禁关闭后才进入发布范围。
4. **生产发布 M5**：Docker Compose/Nginx 与 Electron 安装包在跨端一致性、安全和资源门禁通过后发布。

设备发现、配对、真实设备播放、强度控制和远程控制不属于当前路线图。加入这些能力需要新的 PDR 和独立安全评审。

## 用户承诺

- M1 是可长期使用的自动化入口，不会在 UI 完成后删除 CLI。
- M2 只承诺单文件本地/单请求工作流，不承诺账户、云存储、公开分享或真实设备输出。
- 不能通过真实 App 夹具验证的 QR/规则变换不会以“实验性但默认成功”的形式发布。
- 格式合法性不等同于人体使用安全性。

## 未选择的方案

### 同时开发 Electron 和 Web 的完整编辑器

拒绝。它会在领域语义未稳定时建立两套集成面，延迟第一个可验证闭环。

### 只做浏览器前端并在浏览器解析

拒绝。它会让 Electron/API 复用困难，并与核心逻辑独立于 DOM 的约束冲突。

### 首发包含设备播放

拒绝。设备输出引入授权、强度/时长边界、断连处理和安全责任，不应阻塞文件工具。

## 影响

- CLI、契约与核心测试是 UI 的前置条件。
- PRD 的 P1 是能力优先级，不代表所有 P1 必须无条件进入同一个发布。
- [交付路线图](../plan/delivery-roadmap.md) 是本决策的实施计划。
- 若阶段范围变化，必须先替代本 PDR，再更新追踪矩阵。
