本文规定系统必须提供的技术能力、边界和可验证约束，不规定具体目录结构、UI 框架或第三方库。实现应优先复用项目已有依赖和成熟能力，并保持核心逻辑不依赖 Electron、DOM、Nginx 或具体传输协议。

## 1. 技术目标

- 以 `.pulse` 为唯一规范用户波形文件格式。
- 以纯 TypeScript 领域能力完成解析、校验、展开、插值、编辑和序列化。
- 让 Electron、本地批处理和 Web API 共享相同的领域结果。
- 让所有自动修正、升级和插值都产生可追踪的诊断或变更记录。
- 为文件处理、预览渲染和未来设备 adapter 保持清晰的边界。

## 2. 技术边界

### 2.1 当前范围

- `.pulse` 明文解析与序列化。
- `#DGLAB-PULSE#` QR 封装的识别、还原和生成。
- Pulse 到 WaveformStream 的确定性展开。
- 文件、Pulse、section、stream 和点位级 metadata。
- 结构、范围、语义和版本校验。
- 满足证据门槛后的显式旧版本升级，以及已确认场景中的二次函数插值。
- SVG、PNG、JPG 预览图导出。
- Electron、本地 Node.js 应用服务和 HTTP API 的复用。

### 2.2 当前不属于核心范围

- dglab-kit 的 JSON/JSON5/`.pulses` 文件。
- V2/V3/V4 BLE 或 Socket 传输帧的解析、生成和发送。
- 设备发现、配对、强度控制、远程控制和设备遥测。
- 未确认语义的社区 `.pulse` 方言自动兼容。

研究资料可以描述这些外部协议，但实现不能因研究资料存在就自动扩大支持范围。

## 3. 共享能力边界

系统应按职责分为以下能力层，层之间通过明确的输入、输出和诊断契约通信：

1. **领域层**：Pulse、section、脉冲元、曲线点、WaveformStream、metadata、版本和诊断语义。
2. **应用层**：导入、导出、检查、升级、预览图和修改等用例；负责单文件/批量任务编排、进度、取消和结果聚合。
3. **适配器层**：本地文件、HTTP 上传下载、QR、图像编码、Electron IPC 和未来设备接入。
4. **展示层**：Electron renderer 与 Web 前端；只消费应用层结果，不复制解析或校验规则。
5. **部署层**：Node.js API、静态 Web 和 Nginx；通过 Docker Compose 组合运行。

领域层和应用层不得依赖 Nginx 或浏览器 DOM。适配器失败必须以统一诊断形式返回，不得改变领域结果的语义。

## 4. 规范化数据要求

### 4.1 Pulse

Pulse 是 `.pulse` 文件的规范化内存语义，至少应能表达：

- 原始来源、格式标识、版本或方言判断结果。
- 全局播放参数及其原始值。
- 有序 section、启用状态和 section 级设置。
- 频率定义、频率变化模式和时长定义。
- 脉冲元及其有序强度曲线点。
- 锚点/自动点状态和必要的原始表示信息。
- 展开、修改、升级和导出的诊断/变更信息。

规范化不得将无法确认的字段静默映射为另一个语义。无法判断时应保留原值并产生需要确认的诊断，或拒绝进入可编辑状态。

### 4.2 WaveformStream

WaveformStream 是 Pulse 的派生序列，至少应能表达：

- 有序点位或采样项及其时间位置。
- 每个点位的持续时间、频率、强度和来源 section/脉冲元。
- 点位是原始锚点、自动插值点还是升级补点。
- 展开使用的版本、规则和警告。
- 用于时间轴、统计、播放模拟和图像导出的稳定顺序。

同一个 Pulse 在相同规则和输入下必须得到确定性的 stream。stream 的派生结果不得反向覆盖原始 Pulse；修改必须通过明确的 Pulse 编辑操作完成。

### 4.3 Metadata

metadata 采用分层语义：

- 文件级：路径/名称（如适用）、大小、格式、版本、来源和处理状态。
- Pulse 级：全局设置、section 数量、逻辑时长和整体诊断。
- section 级：频率、模式、目标时长、实际时长、启用状态和脉冲元数量。
- stream 级：点数、总时长、时间粒度、频率/强度统计和展开警告。
- 点位级：时间、持续时间、频率、强度、来源和插值状态。

metadata 展示可以按客户端裁剪，但不能改变字段含义或把诊断降级为无依据的展示文本。

## 5. 解析、序列化与版本要求

### 5.1 解析

- 先识别输入是 `.pulse` 明文、QR 封装还是不支持内容，再进入对应解析流程。
- 解析错误必须包含阶段、位置（文件/section/字段/点位，适用时）和原因。
- 数值解析不得接受超出目标语义的隐式截断、溢出或类型转换。
- 保留需要用于诊断、再次导出或升级的原始信息。

### 5.2 序列化

- 只序列化为当前支持的 `.pulse` 语义或 QR 封装。
- 导出前必须完成适用校验；存在阻断级错误时不得生成成功文件。
- 格式化差异、舍入、补点和版本变化必须可从结果诊断中识别。
- 导入 -> 导出 -> 再导入应满足定义好的语义等价；无法保证时必须报告警告或阻断。

### 5.3 版本升级

- 升级是显式用例，不是导入时的透明兼容层。
- 文件不含可验证版本标识时不得仅凭文件名或 App 名称推断版本；使用明确的 format profile 和 rule
  version。
- 升级输入、目标版本、规则版本、变更项和输出诊断必须可追踪。
- 不覆盖原始文件；输出路径或替换动作由上层应用明确控制。
- 不为已移除的旧路径增加 fallback 或迁移层；不支持的版本应明确拒绝或要求用户执行适用升级。
- 没有真实旧/新夹具、版本识别方法、字段级规则和 App 互操作结果时，不实现该升级路径。

## 6. 插值约束

项目统一使用以下二次函数作为指定的二次插值/递减曲线：

```text
f(x) = 1 - (1 - x) ** 2
```

技术要求：

- `x` 必须是区间内的归一化位置，预期范围为 `[0, 1]`。
- 端点应满足 `f(0) = 0`、`f(1) = 1`。
- 该函数用于构造起止值之间的曲线；具体字段的起止方向由调用场景定义。
- 锚点值不可被自动插值覆盖；自动点使用相邻有效约束计算。
- 结果必须按字段规则取整并裁剪到合法范围，且保留必要的舍入/裁剪诊断。
- 用户编辑中已指定的二次补点统一使用该函数。版本升级只有在对应规则明确要求时才能复用，不能用二次函数猜测未知旧格式。

## 7. 校验与诊断契约

校验至少分为：

1. **识别错误**：无法判断输入类型、版本或方言。
2. **语法错误**：分隔符、字段数量、字符编码或结构不正确。
3. **范围错误**：数值超出允许范围或类型不正确。
4. **语义错误**：结构可解析但不能形成有效 Pulse/stream。
5. **升级警告**：可以升级但存在补点、舍入、丢失或兼容性风险。
6. **导出错误**：目标格式无法表达当前语义或输出失败。

每条诊断至少包含稳定的 code、severity、message、location（如适用）和可选的 suggestion。相同输入和规则版本应得到稳定的 code 与判定结果；UI 可以本地化 message，但不得依赖 message 文本判断逻辑。

## 8. 批量任务要求

- 单文件处理逻辑和批量编排逻辑分离。
- 批量任务必须提供输入计数、完成计数、失败计数、警告计数和取消状态。
- 单文件失败不得污染其他文件的 Pulse、输出或诊断。
- 任务结果应支持逐文件查看，并能关联原始输入、操作、输出和规则版本。
- 服务端必须设置文件数量、文件大小、处理时长和并发资源上限；具体数值在部署前配置并记录。

## 9. 跨端契约

### 9.1 Electron

- Electron 主进程可以访问本地文件和 Node.js 能力。
- renderer 通过明确的 IPC/use case 契约获取任务、metadata、stream 和诊断。
- renderer 不得自行解析 `.pulse` 或复制领域校验规则。
- 离线本地处理不应依赖 Web 服务可用性。

### 9.2 Web

- Node.js API 暴露与 Electron 用例语义一致的处理能力。
- API 输入输出应使用稳定的版本化 schema 和诊断 code；不得直接暴露内部对象引用。
- Web 前端只负责交互与展示，不能因浏览器能力差异改变核心处理结果。
- 上传、下载、任务状态和错误响应必须有明确的大小、超时和权限边界。

### 9.3 一致性

同一规则版本、同一 `.pulse` 内容和同一操作参数，在 Electron、本地 Node 和 Web
API 中应产生等价的 Pulse、WaveformStream、诊断和导出结果。允许存在展示差异，不允许存在未经说明的领域语义差异。

## 10. 预览与导出要求

- 时间轴必须以稳定的时间顺序展示 stream，并能关联回 Pulse 来源。
- hover 信息必须来自 stream/metadata 数据，不得从视觉近似值反推。
- 环形频谱与颜色映射必须同时提供可读数值或替代文本，满足不可只依赖颜色的要求。
- SVG、PNG、JPG 导出的同一 stream 应使用同一数据快照和同一坐标语义。
- 播放模拟应可暂停、停止、定位或显示进度，并明确标记为本地预览，不触发设备输出。

## 11. 部署与运行要求

- 生产交付使用 Docker Compose 组合 Web、Node.js API 和 Nginx。
- Nginx 负责静态资源、TLS/反向代理配置边界和 API 路由转发，不承载 Pulse 领域逻辑。
- API 与 Web 可以独立扩展和更新；两者之间的 schema 必须可验证。
- 容器必须支持健康检查、优雅停止和可观察的启动失败原因。
- 文件临时目录、持久化目录和日志目录必须有明确的生命周期与权限策略。
- Electron 发布包应包含核心处理能力，不把本地基础工作流强制绑定到 Web 服务。

## 12. 安全与隐私要求

- 解析器必须限制输入大小、嵌套/展开规模和处理时间，防止资源耗尽。
- QR/文件解码失败必须安全退出，不执行文件内容中的任意指令。
- Web 服务必须在上线前确定鉴权、上传访问、删除和保留策略。
- 日志默认不记录完整波形内容；诊断日志应避免暴露敏感文件名和用户数据。
- 真实设备 adapter 如上线，必须有显式用户确认、强度/时长上限和断连处理；它不属于当前核心处理链。

## 13. 可验证性与测试要求

- 解析、序列化、校验、展开和插值必须可在无 UI 环境独立测试。
- 建立合法、边界、非法、旧版本、QR 损坏和不可判定方言的固定样例。
- 每个支持版本至少有导入、导出、再导入和语义等价测试。
- 插值测试必须覆盖端点、单点、多点、锚点、边界裁剪和取整。
- Electron、Node API 和批处理至少共享一组跨端一致性测试。
- 批量任务测试必须覆盖部分失败、取消、重复输入和输出冲突。
- 图像导出测试至少验证非空输出、尺寸、关键图形元素和 stream 数据一致性。

## 14. 技术决策待定项

- HTTP schema 库和图像编码库的具体选择；必须按 [ADR-0003](adr/0003-versioned-boundary-contracts.md)
  的边界验证官方类型和运行环境。
- 频率索引映射、播放速度影响和物理单位展示策略。
- 满足证据门槛后的具体升级规则表。
- 真实设备 adapter 的协议、权限和安全评审结果。

这些决策不得改变本文已确定的格式边界、核心层独立性和诊断可追踪性要求。
